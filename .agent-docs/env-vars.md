# Environment Variables

The root `.env` is the **single source of truth** for local values. `.env.example` is the source of truth for documentation — every variable is listed there with a description. `bun run setup:env` consumes `.env` and writes per-workspace artifacts; do not hand-edit those artifacts.

## Wrangler env-var mechanisms

| Mechanism | What goes here | Committed? |
|-----------|----------------|------------|
| `vars` in `wrangler.jsonc` | Non-secret config (development defaults). Host-derived keys are merged in by `setup:env`. | Yes |
| `.dev.vars` | Secrets for local dev (`wrangler dev` reads them). | No (gitignored) |
| `.dev.vars.tenancy` | Generated tenancy dev flags (`ALLOW_DEV_TENANT_HEADER`, `ALLOW_DEV_TENANT_AUTH`). Sourced by the dev shell that boots `wrangler dev`. | No (gitignored) |
| `wrangler secret put KEY` | Secrets in production. | No (Cloudflare dashboard) |
| `--var KEY:value` at deploy | Production overrides for non-secret vars. | No (in CI script) |

### Why not wrangler environments?

Wrangler `env.*` blocks do NOT inherit bindings (KV, Hyperdrive, services, queues, durable objects). Using them would force duplicating every binding. The `--var` flag at deploy time avoids this.

### Why not `.dev.vars` for `NODE_ENV`?

`.dev.vars` is for secrets only. When `secrets.required` is set in `wrangler.jsonc`, wrangler only loads keys listed there from `.dev.vars`; other keys are silently ignored.

## Local development

`wrangler dev` reads vars directly from `wrangler.jsonc`. Top-level `vars` carry development defaults. Secrets come from `.dev.vars` (generated by `bun run setup:env` from the root `.env`). Host-derived keys arrive in two ways: written to `wrangler.jsonc.fragment.json` (audit artifact) AND merged into `wrangler.jsonc` `vars` in place.

## Production deployment

Each worker's `deploy` script in `apps/*/package.json` already passes `--var NODE_ENV:production`. When deploying to a real environment, also override `APP_URL`, `CORS_ORIGINS`, and any host-derived value that differs from the local default:

```bash
wrangler deploy --minify \
  --var NODE_ENV:production \
  --var APP_URL:https://api.example.com \
  --var CORS_ORIGINS:https://example.com
```

Production secrets are set once via `wrangler secret put KEY`.

## Adding a new env var

- **Non-secret, same in all environments**: add to `vars` in `wrangler.jsonc` and document in `.env.example`.
- **Non-secret, differs per environment**: add to `vars` with a dev default and add a `--var` override to the `deploy` script.
- **Secret**: add to `secrets.required` in `wrangler.jsonc`, list in `.dev.vars` locally, run `wrangler secret put` for production, document in `.env.example`, and update `scripts/setup-env.sh` if it should be copied automatically.
- **Host-derived**: edit `.env`, then re-run `bun run setup:env`. Never hand-edit the fragment or `wrangler.jsonc` `vars` block — `bun run check:hosts` will fail.

### `apps/server`
- Vars: `NODE_ENV`, `APP_URL`, `CORS_ORIGINS`, `EMAIL_FROM`, `APP_NAME`, `COMPANY_NAME`, `SUPPORT_EMAIL`, `LOGO_TEXT`, `BRAND_PRIMARY_COLOR`, `FCM_PROVIDER`, `WILDCARD_SUFFIX`, `ADMIN_HOST`, `FALLBACK_HOST`, `LOCAL_DEV_HOSTS`, `BRANDING_BASE_URL`, `CLOUDFLARE_ZONE_ID`, `CUSTOM_HOST_CNAME_TARGET`, `CUSTOM_HOST_VERIFICATION_LABEL`, `BRANDING_HOST`.
- Secrets (required): `FIREBASE_SERVICE_ACCOUNT_KEY_BASE64`, `RESEND_API_KEY`, `VAULT_MASTER_KEY`, `SSO_KEY` (pgcrypto key for encrypted OIDC config), `CLOUDFLARE_API_TOKEN` (zone-scoped, three permissions only).

### `apps/auth`
- Vars: `NODE_ENV`, `APP_URL`, `CORS_ORIGINS`, `WILDCARD_SUFFIX`, `ADMIN_HOST`, `LOCAL_DEV_HOSTS`, `EMAIL_FROM`, `APP_NAME`, `COMPANY_NAME`, `SUPPORT_EMAIL`, `LOGO_TEXT`, `BRAND_PRIMARY_COLOR`, `FALLBACK_HOST`.
- Secrets (required): `BETTER_AUTH_SECRET`, `RESEND_API_KEY`.

### `apps/admin`
- Vars: `NODE_ENV`, `ADMIN_HOST`. The dev-only `ALLOW_DEV_ADMIN_AUTH` and `LOCAL_DEV_ADMIN_EMAIL` flags are **never committed**; they are injected only via the dev fragment. A startup guard in `apps/admin/src/server.ts` 500s every request if either flag leaks into a production env (D52 / Wave-2 audit fix).
- Secrets (required): `CF_ACCESS_AUD`, `CF_ACCESS_TEAM_DOMAIN`.

### `apps/app`
- No secrets. `wrangler.jsonc` declares only the public routes plus the `ASSETS` and `API` bindings.

## Host-derived `vars`: fragment + merge

A subset of each worker's `vars` block is host-derived (`WILDCARD_SUFFIX`, `ADMIN_HOST`, `FALLBACK_HOST`, `LOCAL_DEV_HOSTS`, `CUSTOM_HOST_*`, `BRANDING_HOST`). These keys come out of `scripts/lib/host-config.ts` and are written to two places by `bun run setup:env`:

1. **`apps/<worker>/wrangler.jsonc.fragment.json`** — canonical generated artifact. Useful as an audit trail and as input for CI parity checks.
2. **`apps/<worker>/wrangler.jsonc`** — the live config Wrangler reads. Only the `vars.<KEY>` leaves are patched; surrounding comments, `services`, `secrets`, etc. are left untouched (the merger uses `jsonc-parser` so JSONC trivia survives).

This keeps `wrangler.jsonc` as the single source of truth for non-Wrangler tooling (linters, IDE, OpenAPI gen) without forcing operators to hand-merge the fragment. CI runs `bun run check:hosts` which fails with a `wrangler-vars-parity` drift entry if the two ever disagree.

To change a host-derived value, edit the root `.env` and re-run `bun run setup:env`. Hand-edits to either the fragment or the `wrangler.jsonc` `vars` block will trip the parity check on the next `bun run check`.
